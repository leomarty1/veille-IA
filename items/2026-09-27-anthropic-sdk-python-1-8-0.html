Contexte étendu

Le SDK Python d'Anthropic passe en 1.8.0 le 22 septembre, synchronisé avec la sortie d'Opus 5.5. Côté fonctionnalités, la version ajoute le support de claude-opus-5-5, les définitions d'outils en ligne et l'épinglage de liste d'outils MCP en bêta — c'est-à-dire l'exposition, côté client typé, des deux nouveautés d'API du même jour. La progression est rapide : 1.5.0 le 13 septembre, 1.6 et 1.7 la semaine suivante, 1.8.0 le 22.

Les correctifs sont plus intéressants que les ajouts pour qui fait tourner des agents. add_tools() prend désormais effet immédiatement (issue #874) au lieu de n'être visible qu'au tour suivant — un décalage qui, dans une boucle agentique, se traduisait par un tour perdu à chaque fois qu'un outil était ajouté dynamiquement. Le tool runner laisse maintenant de côté les paramètres réservés aux réponses dans sa requête de compaction (#871), ce qui corrige des échecs de compaction en milieu de tâche longue. Enfin, un plantage à la sortie de l'interpréteur sous Python 3.13, déclenché quand un flux de streaming restait ouvert, est corrigé : il touchait typiquement les scripts qui sortent sur exception sans fermer proprement leur stream.

Le reste est de la consolidation : un même énuméré evaluated_permission partagé par tous les événements Managed Agents plutôt qu'un par événement, et une série de mises à jour de documentation sur les références API Dreams, User Profiles et les memory stores des Managed Agents.

🛠 Pourquoi c'est utile à savoir pour Lynxter

Le correctif add_tools() est celui qui change quelque chose dans une boucle d'agent. Si le pipeline de support ajoute des outils en cours de traitement — ce que les définitions d'outils en ligne du 22 septembre rendent justement pertinent — la version antérieure perdait un aller-retour complet avec le modèle à chaque ajout. À $4/M en entrée sur Opus 5.5, un tour perdu sur un prompt de support chargé n'est pas gratuit. Action : épingle anthropic>=1.8.0 dans les dépendances du pipeline avant de commencer à ajouter des outils dynamiquement.

Le plantage Python 3.13 mérite une vérification de version d'interpréteur. Le symptôme — un plantage à la sortie quand un flux de streaming n'a pas été fermé — est du genre à passer pour un problème de code applicatif et à coûter une demi-journée de recherche. Action : si des scripts de la chaîne de veille ou du pipeline support tournent sous Python 3.13 avec du streaming, monte le SDK plutôt que de chercher la fuite ailleurs.

Réserve. Les deux nouveautés exposées (outils en ligne, épinglage MCP) sont en bêta côté API et le restent côté SDK : disposer du support typé ne les rend pas contractualisables. Action : traite 1.8.0 comme une mise à jour de maintenance à faire maintenant, et les fonctions bêta comme un sujet de prototype séparé.
