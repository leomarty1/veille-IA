Contexte étendu

Jusqu'ici, un agent Managed se créait et se modifiait par appels d'API ou par la console : reproductible à la main, pas par un dépôt. ant apply (CLI ant 1.30.0, notes de version du 3 septembre) change le modèle : chaque ressource — agent, environnement, skill, memory store, déploiement — est décrite dans un fichier, la commande calcule un plan, l'affiche, et l'applique après approbation. Le schéma est celui d'un outil d'infrastructure as code, plan compris.

La pièce qui rend la chose utilisable en équipe est le lockfile claude-lock.json, écrit après application et destiné à être commité. C'est lui qui fait qu'un run ultérieur — sur une autre machine ou dans un pipeline CI — met à jour les mêmes ressources au lieu d'en créer de nouvelles. Sans lui, chaque exécution produirait des doublons ; avec lui, le dépôt devient la source de vérité de la configuration d'agents, et un git revert redevient un moyen de revenir en arrière sur un agent en production.

🛠 Pourquoi c'est utile à savoir pour Lynxter

C'est la réponse à une question de gouvernance qui se pose dès qu'il y a deux agents. Un agent de tri de tickets et un agent de diagnostic partagent des skills, des memory stores et des environnements ; les modifier à la console, c'est perdre l'historique et ne plus savoir qui a changé quoi. Déclarés en fichiers dans le même dépôt que les prompts, ils passent en revue de code comme le reste. Action concrète : décrire l'agent de support actuel en fichiers ant apply, commiter le lockfile, et vérifier qu'un second apply ne crée rien — c'est le test qui prouve que le dépôt est bien la source de vérité.

Ne pas en faire un critère de choix de fournisseur sans vérifier la concurrence. Codex cloud et les cloud agents Cursor ont leurs propres mécanismes de configuration ; je n'ai pas pu ouvrir leurs changelogs cette semaine (egress bloqué) pour dire s'ils offrent un flux déclaratif avec lockfile équivalent. À contrôler avant de l'écrire dans un argumentaire.
