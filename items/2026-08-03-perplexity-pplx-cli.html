pplx — CLI mono-binaire qui expose la Search API de Perplexity en JSON aux agents de code

Contexte étendu

Le CLI pplx tient en un binaire et deux commandes. pplx search web interroge la Search API avec des filtres qui sont exactement ceux dont un agent a besoin pour cadrer une recherche : --domains pour restreindre à une liste de sites, --recency-filter et le couple --published-after-date/--published-before-date pour la fenêtre temporelle, --country, et --search-context-size pour doser le volume ramené. pplx content snippets fait l'extraction ciblée sur jusqu'à 50 URLs par appel, avec --max-tokens réglable de 1 à 16 384 (défaut 4 096). Le contrat de sortie est le point important : exit code 0 et exactement un objet JSON sur stdout, de forme {hits:[{url,title,domain,snippet}], total}, directement pipeable vers jq.

Ce que pplx n'est pas mérite d'être souligné, parce que c'est contre-intuitif venant de Perplexity : pas de mode conversationnel, pas de sélection de modèle, pas de réponse synthétisée. C'est une couche de retrieval déterministe — l'outil ramène des documents, pas une opinion. Pour un agent, c'est exactement la bonne primitive : la synthèse est déjà le travail du modèle appelant, ce qui manquait était une recherche dont la sortie soit stable, filtrable et parsable sans heuristique.

La distribution est soignée mais étroite. L'installeur vérifie le SHA-256 et pose le binaire dans ~/.local/bin/pplx sans sudo, avec un pplx update atomique. La couverture se limite à trois cibles — macOS Apple Silicon, Linux x86_64, Linux arm64 : ni Windows, ni macOS Intel. pplx auth login est TTY-only, donc toute exécution non interactive (agent, CI, cron) doit exporter PERPLEXITY_API_KEY. Une Agent Skill packagée est fournie pour Claude et les autres agents de code, et la facturation de la Search API est annoncée à 5,00 $ pour 1 000 requêtes, plafonnée à 50 QPS sur tous les paliers — ce dernier chiffre venant d'une source secondaire.

🎯 Pourquoi c'est important pour Lynxter

C'est le chaînon manquant pour du grounding web reproductible dans Claude Code. Aujourd'hui, quand une routine a besoin d'une information externe — une fiche technique fournisseur silicone, une norme, une révision de doc machine, un communiqué constructeur — on laisse un modèle improviser une recherche et on récupère une synthèse dont on ne sait pas d'où elle vient. Avec pplx, la routine émet une requête cadrée (--domains sur les sites fournisseurs et normalisateurs, --published-after-date pour ne pas ressortir une révision périmée) et reçoit une liste d'URLs avec snippets, que le modèle traite ensuite explicitement. La chaîne devient auditable : on peut rejouer la même requête et comparer.

Le modèle de coût change la façon de dimensionner. 5,00 $ pour 1 000 requêtes, c'est un coût par appel prévisible, indépendant du volume de tokens ramené — l'inverse d'une facturation au token où une recherche verbeuse coûte cher sans prévenir. Pour la routine veille elle-même, pour un enrichissement de base de connaissances support, ou pour vérifier périodiquement qu'une doc fournisseur n'a pas changé, le budget se calcule au nombre de requêtes planifiées. Le plafond de 50 QPS n'est pas une contrainte à notre échelle.

Deux réserves opérationnelles à intégrer avant de standardiser. D'abord l'absence de binaire Windows : les postes atelier sont sous Windows, donc tout usage y passe par WSL ou par un poste Linux/macOS de rebond — à trancher avant de mettre pplx dans une procédure destinée aux techniciens. Ensuite l'auth TTY-only : pplx auth login ne fonctionne pas dans un run non interactif, il faut donc gérer PERPLEXITY_API_KEY comme un secret d'environnement — et, au vu des post-mortems Anthropic et OpenAI de cette même semaine, ne surtout pas le déposer dans un fichier du workspace visible par l'agent.
