Contexte étendu

Le modèle de clés d'API par espace de travail a un défaut structurel connu : la clé survit à la personne. Quelqu'un quitte l'équipe, son compte est désactivé, et la clé qu'il avait créée continue de fonctionner — souvent sans que personne ne sache à quoi elle sert ni ce qu'elle consomme. Les clés personnelles et clés de compte de service introduites le 27 août règlent cela par construction : elles agissent au nom de l'utilisateur ou du compte de service, avec exactement ses permissions, et cessent de fonctionner quand le compte lié est retiré de l'organisation. Anthropic met en avant les deux effets recherchés : suivre la consommation par compte, et vérifier que l'usage d'une clé est légitime. La granularité reste souple — une clé peut être limitée à un espace de travail, ou porter sur les endpoints d'administration et l'ensemble des espaces auxquels le compte a accès. Les clés d'espace de travail restent supportées, en option héritée.

Le 26 août, l'Admin API sort du domaine réservé au curl : elle devient accessible depuis la CLI ant et les SDK Python, TypeScript, C#, Go, Java, PHP et Ruby, sous client.beta.organization. Le périmètre couvre les informations d'organisation, les membres, les invitations, les espaces de travail et leurs membres, les clés d'API, les limites de débit, les comptes de service, les émetteurs et règles de fédération d'identité de charge de travail, et les clés de chiffrement gérées par le client. Restent en curl uniquement : les rapports d'usage et de coût, et les endpoints de gestion d'utilisateurs et d'analytique de Claude Enterprise. L'authentification accepte une clé Admin API via ANTHROPIC_API_KEY ou un jeton OAuth org:admin via ANTHROPIC_AUTH_TOKEN.

Le troisième volet est une rupture de compatibilité à surveiller dans les SDK Python 1.2.0, TypeScript 0.122.0, Go 1.68.0, Java 2.59.0, Ruby 1.67.0 et C# 12.44.0 : client.beta.files et client.beta.skills n'envoient plus les headers files-api-2025-04-14 et skills-2025-10-02 et renvoient les mêmes formes que leurs équivalents non-beta. Deux conséquences concrètes : client.beta.skills.delete() supprime désormais une Skill avec toutes ses versions — un comportement nettement plus destructeur qu'avant — et le type Messages BetaSkill (la référence de Skill de conteneur) est renommé BetaContainerSkill. Les requêtes qui envoient encore les headers beta continuent de recevoir les formes beta, ce qui laisse une porte de sortie le temps de migrer.

🛠 Pourquoi c'est utile à savoir pour Lynxter

C'est le moment de faire l'inventaire des clés. La question à poser n'est pas « combien de clés avons-nous » mais « pour chaque clé, qui l'a créée, ce qu'elle alimente, et ce qui se passe si cette personne part ». Toute clé d'espace de travail qui survit à son créateur est un point de fuite silencieux et une ligne de facture non attribuée. La migration vers des clés personnelles pour les usages humains et des clés de compte de service pour les automatisations donne un modèle où la révocation est un effet de bord de la gestion RH, pas une tâche à ne pas oublier.

Attention au piège de skills.delete(). Si un script d'outillage appelle client.beta.skills.delete() — typiquement pour faire du ménage entre deux déploiements —, son comportement a changé : il supprime maintenant la Skill et toutes ses versions. Un script écrit sous l'ancienne sémantique peut détruire un historique qu'on croyait conservé. Vérifiez avant de monter les SDK. Et si vous migrez un outillage qui envoie encore les headers beta, faites-le en une passe : les deux comportements coexistent aujourd'hui, mais dépendre de cette coexistence est une dette.
