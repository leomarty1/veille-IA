Contexte étendu

Le changelog code.claude.com couvre v2.1.216 (20 juil.) à v2.1.219 (24 juil.). Le point structurant est v2.1.219, qui accompagne la sortie d'Opus 5 : claude-opus-5 devient le défaut Opus (contexte 1M, fast mode $10/$50). Deux changements d'orchestration : la profondeur d'imbrication des subagents passe de 1 à 3 par défaut (réglable via CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH) — un orchestrateur peut déléguer à un sous-agent qui délègue à son tour — et des caps de session plafonnent les cascades à 200 spawns de subagents par session et 20 concurrents, garde-fous anti-runaway sur les runs mal cadrés.

v2.1.219 ajoute aussi sandbox.network.strictAllowlist, qui restreint le sandbox réseau des sous-agents aux seuls domaines explicitement autorisés — durcissement pour exécuter du code non fiable sans risque d'exfiltration. v2.1.218 (22 juil.) passe /code-review en subagent d'arrière-plan (dans la lignée du /code-review et /verify sur invocation explicite du brief précédent) et corrige un coût de normalisation de messages devenu quadratique en session longue — gain de latence net sur les sessions qui accumulent l'historique.

v2.1.217 et v2.1.216 sont des correctifs de robustesse : fuites mémoire (les sorties MCP tronquées gardaient le résultat complet en mémoire) et une régression de perf provoquant des stalls multi-secondes au resume de session. La cadence — 14 releases 2.1.202→215 la semaine précédente, puis 216→219 cette semaine — confirme un rythme d'itération quasi-quotidien sur Claude Code, avec un focus alternant features d'orchestration et durcissement mémoire/sandbox.

🎯 Pourquoi c'est important pour Lynxter

depth 3 + caps débloquent des pipelines support réels tout en les bornant. L'imbrication à depth 3 permet enfin des orchestrations à trois niveaux : agent de tri → agent de parsing de logs machine → agent de rédaction de réponse, sans aplatir le pipeline dans un seul orchestrateur qui sature son contexte. Les caps (200 spawns, 20 concurrents) garantissent qu'un run de diagnostic mal formulé ne draine pas le budget en spawnant à l'infini — indispensable avant d'ouvrir ces workflows à l'équipe support. Action : structure ton diagnostic support S300X/S600D en trois niveaux de subagents et mesure le coût plafonné d'un run complet sur un ticket réel.

strictAllowlist est le prérequis pour exécuter du code client en sandbox. Sur les workflows où un utilisateur fournit un script de calibration, un parseur de gcode ou un dump de logs, sandbox.network.strictAllowlist te laisse restreindre le réseau aux seuls domaines nécessaires — aucune exfiltration possible vers un endpoint tiers. Câble une allowlist minimale sur ton profil Claude Code support (registres de packages internes + API Anthropic uniquement), teste un run de parsing sur un dump client, et fais-en le profil standard avant tout run touchant des données client. Le correctif quadratique de v2.1.218 aide en prime sur les sessions support longues qui accumulent l'historique de conversation.
