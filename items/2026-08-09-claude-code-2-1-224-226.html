Contexte étendu

La 2.1.224 du 7 août est la version structurante des trois. Elle ouvre les environnements self-hosted : la commande claude self-hosted-runner enregistre une machine ou un conteneur comme cible d'exécution pour les sessions Claude Code lancées depuis le web, le mobile ou le desktop. Jusqu'ici, ces surfaces impliquaient une exécution sur l'infrastructure d'Anthropic ; désormais le code, le réseau interne et l'outillage maison restent chez toi, avec les contrôles de conformité qui vont avec. La fonctionnalité est réservée aux plans Team et Enterprise. La même version supprime le plafond de 200 sous-agents par session — les sessions longues ne refusent plus de nouveaux agents, les limites de concurrence et de profondeur restant en vigueur — et introduit le SendMessage inter-sessions : deux sessions Claude Code peuvent se parler, y compris sur des machines différentes, ListAgents servant à les découvrir (macOS et Linux). La 2.1.225 étend ce mécanisme pour démarrer une conversation avec une session Remote Control d'une autre machine par son nom, au lieu de ne pouvoir répondre qu'après avoir été contacté.

Le volet sécurité de la 2.1.224 mérite une lecture attentive. Deux défauts du sandbox sont corrigés : d'une part, les entrées de refus filesystem écrites avec un slash final — typiquement denyRead: "~/.aws/" — étaient silencieusement contournables sur Linux et macOS, c'est-à-dire qu'une configuration qui semblait protéger les credentials AWS ne protégeait rien ; d'autre part, les détails d'une violation du sandbox n'apparaissaient jamais dans les résultats de l'outil Bash, si bien que le modèle ne savait pas quel accès lui avait été refusé et pouvait boucler. S'y ajoutent de nouvelles options de masquage de credentials : extract et onExtractNoMatch pour les valeurs d'environnement structurées, decode: "jwt" couplé à maskClaims pour un masquage conscient de la structure d'un JWT, et awsPairs/sigv4 pour re-signer les requêtes AWS SigV4. Ces options exigent network.tlsTerminate et ne sont honorées que depuis les settings utilisateur, managés ou --settings — un projet ne peut pas se les auto-attribuer. Enfin, un bug de collision de répertoires de session sur les chemins de projet longs (plus de 200 caractères) est corrigé : liste, renommage, fork, suppression et /resume ne traversent plus les projets.

Les 2.1.225 et 2.1.226 du 8 août sont des versions d'exploitation. La 2.1.225 apporte le support des plafonds de dépense gateway dans l'avertissement d'usage — le message de limite atteinte nomme le plafond, son heure de réinitialisation et le message de l'opérateur, à condition que le gateway soit lui-même en 2.1.225 — et ajoute un prompt de confiance d'espace de travail à claude agents pour les répertoires non fiables, alignant son comportement sur celui de claude. Trois correctifs touchent des scénarios d'automatisation : un 401 transitoire remplaçant un CLAUDE_CODE_OAUTH_TOKEN longue durée par le token court d'un login stocké cassait les sessions headless jusqu'au redémarrage ; les serveurs MCP OAuth sous macOS renvoyaient par intermittence une rafale de 401 comme s'ils n'avaient jamais été authentifiés, après expiration d'une lecture du keychain ; et le mode auto comptait le refus par filtre de sécurité de sa propre vérification de permission dans la limite de blocages consécutifs — l'action reste refusée, mais le modèle est désormais invité à passer à autre chose plutôt qu'à réessayer. La 2.1.226 ne contient que des correctifs de fiabilité.

🎯 Pourquoi c'est important pour Lynxter

Le runner self-hosted est ce qui manquait pour faire entrer les dépôts firmware dans le périmètre agent. L'objection tenait en une phrase : le code S300X/S600D ne sort pas du réseau. Elle tombe. Monte un runner sur une machine de l'atelier ou un conteneur du réseau interne, enregistre-le, et les sessions démarrées depuis le mobile ou l'interface web s'exécutent dessus, avec accès au NAS et aux outils maison. Action concrète cette semaine : provisionne un runner sur une machine de test, lance une session triviale depuis le téléphone (lister les profils de calibration), et vérifie surtout le chemin d'échec — la 2.1.224 corrige précisément un cas où un --base-dir impossible à créer ou à écrire laissait le runner s'enregistrer puis échouer à chaque session, sans erreur exploitable ; il sort maintenant au démarrage avec un message clair. Vérifie aussi que le plan couvre la fonctionnalité : elle est limitée à Team et Enterprise.

Audite tes configurations sandbox aujourd'hui, pas à la prochaine revue. Le correctif du slash final n'est pas cosmétique : toute règle du type denyRead: "~/.aws/", denyWrite: "/etc/" ou équivalente écrite avec un séparateur terminal était contournable en silence sur Linux et macOS. Si une session Claude Code a tourné en mode permissif sur une machine portant des credentials, la protection que tu croyais active ne l'était pas. Passe en revue les entrées denyRead/denyWrite de tes settings, retire les slashs terminaux, et profite des nouvelles options de masquage : decode: "jwt" avec maskClaims pour les tokens de l'API support, awsPairs/sigv4 si des scripts signent des requêtes S3. Attention au prérequis : ces options ne s'activent qu'avec network.tlsTerminate, et uniquement depuis les settings utilisateur, managés ou passés en --settings. Bonus opérationnel : les violations du sandbox remontent enfin dans les résultats Bash, ce qui rend débogable un agent qui bloque au lieu de le voir tourner en rond.

La suppression du plafond de 200 sous-agents et le SendMessage inter-sessions changent l'échelle de ce que tu peux orchestrer. Le plafond mordait sur les sessions longues — typiquement une routine de veille ou un audit qui fan-out par acteur ou par fichier et finit par se voir refuser de nouveaux agents. Il n'existe plus ; seules la concurrence et la profondeur restent bornées. Le SendMessage inter-sessions ouvre autre chose : une session sur la machine de l'atelier (accès imprimantes, NAS) peut échanger avec une session sur ton poste, découverte via ListAgents. Le pattern utile pour Lynxter : une session « terrain » qui collecte des logs machine et une session « analyse » qui les traite, sans passer par un fichier partagé. Deux garde-fous à connaître avant de le mettre en production : les messages envoyés vers une session tournant en permissions bypassées sont retenus pour approbation (crossSessionInbound, dialogExpiry), et la 2.1.224 corrige un SendMessage qui annonçait « Message sent » alors que l'écriture dans la boîte du destinataire avait échoué — les échecs de livraison sont désormais remontés comme erreurs.
