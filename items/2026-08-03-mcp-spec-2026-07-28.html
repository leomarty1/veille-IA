MCP 2026-07-28 — le protocole passe stateless, extensions versionnées et auth alignée OAuth/OIDC

Extrait du brief MCP passe stateless, les labos avouent leurs évasions — 2026-08-03

Chiffres clés

0handshake
initialize/initialized et Mcp-Session-Id supprimés
12mois
Support minimum garanti sur Roots, Sampling, Logging, HTTP+SSE
4SDK Tier 1
TypeScript, Python, Go, C# au jour du lancement (Rust beta)
ttlMs+ cacheScope
Cache calqué sur HTTP Cache-Control sur tous les listings

Contexte étendu

La révision 2026-07-28 est la plus lourde depuis la publication initiale du Model Context Protocol. Le changement structurant est l'abandon du modèle bidirectionnel stateful : plus de handshake initialize/initialized, plus d'en-tête Mcp-Session-Id. Chaque requête devient autoportante — elle transporte sa version de protocole, l'identité du client et ses capabilities en métadonnées. Conséquence d'infrastructure immédiate : un serveur MCP n'a plus besoin d'affinité de session, donc il se déploie derrière un load-balancer round-robin, en serverless ou en edge, sans stockage partagé entre instances. Le corollaire est que les requêtes serveur→client, qui supposaient un canal ouvert, disparaissent : elles sont remplacées par le Multi Round-Trip Request — le serveur répond resultType: "input_required", le client rejoue le même appel enrichi d'inputResponses. Un serveur qui a besoin d'une élicitation utilisateur ou d'une confirmation en cours d'exécution doit donc être réécrit pour être rejouable, pas seulement reconfiguré.

Deux ajouts visent explicitement l'exploitation en production. Le premier est le cache : tools/list, prompts/list, resources/list et resources/read renvoient désormais ttlMs et cacheScope, une sémantique directement calquée sur HTTP Cache-Control — un catalogue d'outils ou une base documentaire stable cesse d'être rechargée à chaque tour de boucle agentique. Le second est le routage : les en-têtes Mcp-Method et Mcp-Name exposent la méthode et la cible en clair, ce qui permet à une gateway, un WAF ou un rate-limiter de router et de compter sans désérialiser le corps JSON-RPC. Côté autorisation, la spec durcit l'alignement OAuth/OIDC : validation d'issuer conforme à la RFC 9207, credentials liés au serveur d'autorisation émetteur, paramètre application_type ajouté au Dynamic Client Registration — lequel est dans le même mouvement formellement déprécié au profit des Client ID Metadata Documents, où le client publie ses métadonnées à une URL au lieu de s'enregistrer dynamiquement.

Le troisième axe est la gouvernance des fonctionnalités. Tasks sort du cœur expérimental pour devenir une extension versionnée, io.modelcontextprotocol/tasks, avec tasks/get en polling et un nouveau tasks/update — le protocole adopte donc un modèle noyau stable + extensions nommées, ce qui évite que chaque capacité émergente déstabilise la spec centrale. En face, la liste de dépréciations est longue : Roots, Sampling, Logging et le transport legacy HTTP+SSE, tous couverts par une fenêtre de support minimale annoncée de 12 mois. Les quatre SDK Tier 1 — TypeScript, Python, Go, C# — supportent la spec dès le jour du lancement, Rust reste en beta. Anthropic accompagne la sortie d'un billet annonçant le déploiement progressif du support dans les produits Claude : connecteurs à UI embarquée, authentification managée pour l'entreprise, observabilité et tunnels réseau privés — c'est-à-dire la partie qui rend un serveur MCP interne accessible depuis Claude sans l'exposer sur internet.

🎯 Pourquoi c'est important pour Lynxter

Audit à faire maintenant sur chaque serveur MCP maison branché sur Claude Code. Les candidats sont connus : base de connaissances support S300X/S600D, connecteur tickets, doc machines et procédures, passerelle ERP. Trois grep suffisent à cadrer l'effort — Mcp-Session-Id et initialize (état par session, cassé par le stateless), sampling/ et roots/ (dépréciés, 12 mois de sursis), et tout ce qui suppose un canal serveur→client ouvert (à reprendre en Multi Round-Trip : renvoyer resultType: "input_required" et traiter le rejeu avec inputResponses comme une exécution idempotente). Le point de vigilance est la rejouabilité : un serveur qui écrivait un ticket avant de demander confirmation doit devenir sûr à rejouer, sinon la migration produit des doublons en base.

Le gain d'exploitation est réel et arrive gratuitement. Sans session, les serveurs MCP internes n'ont plus besoin d'un process long-lived : ils passent en fonction serverless ou derrière un simple round-robin, ce qui supprime le point de défaillance unique d'un connecteur maison hébergé sur une VM. Et ttlMs/cacheScope sur les listings est directement applicable à notre cas : un catalogue d'outils ou une doc machine ne change qu'à chaque release firmware, un TTL de plusieurs heures y est trivialement correct et réduit d'autant les tokens consommés à chaque itération d'un agent long. À l'inverse, un connecteur tickets doit rester à TTL court ou nul — le cacheScope est là pour distinguer les deux, il faut le renseigner explicitement plutôt que de laisser le défaut décider.

Le volet auth conditionne l'ouverture à des clients ou des partenaires. La validation d'issuer RFC 9207 et les credentials liés au serveur d'autorisation émetteur ferment la classe d'attaques où un token obtenu pour un serveur est rejoué contre un autre — c'est la précondition pour envisager un jour d'exposer un serveur MCP Lynxter (doc machine, catalogue de profils d'impression, statut de commande de consommables) à un client sous NDA plutôt qu'à nos seuls postes internes. Dans l'intervalle, la dépréciation du Dynamic Client Registration au profit des Client ID Metadata Documents est le détail à noter dans la roadmap : toute intégration écrite aujourd'hui contre le DCR devra être reprise, autant partir directement sur CIMD. Enfin, le déploiement annoncé côté Claude des tunnels réseau privés est à surveiller — c'est ce qui permettrait de brancher l'ERP sans le sortir du réseau interne.
