Contexte étendu

Le SDK Python d'Anthropic suit la plateforme à quelques jours près, et les deux versions de la semaine sont surtout la traduction en code de ce qui a été annoncé côté API. La 1.6.0 (15 septembre) apporte les permissions d'outils auto mode pour les Managed Agents — le pendant SDK de ce que la plateforme avait exposé le 10 septembre — ainsi que le paramètre compaction et les blocs signés en beta, annoncés le 14. S'y ajoutent url_sources sur l'outil web fetch, un workspace_id sur les méthodes de profil utilisateur, des types énumérés pour les champs géographiques de résidence de données d'un workspace, et le support de fournisseurs de jetons d'identification asynchrones.

Le lot de correctifs de la 1.6.0 mérite d'être lu pour lui-même, parce qu'il touche le comportement sous charge. Le client honore désormais les valeurs de Retry-After supérieures à 60 secondes au lieu de les plafonner, ignore les valeurs invalides plutôt que de s'y fier, valide maxRetries, et — le plus important pour un agent long — rejoue les erreurs de connexion dans le client asynchrone sans bloquer la boucle de retry dans la coroutine. Un agent qui tourne longtemps derrière un réseau instable perdait des runs sur ce défaut.

La 1.7.0 (18 septembre) est plus courte mais referme la boucle de la compaction : compact_before_next_turn() entre dans le tool runner, la primitive qui exécute une boucle agentique sur des outils fournis par l'appelant. La compaction serveur annoncée le 14 cesse d'être un appel à orchestrer soi-même pour devenir une méthode de la boucle. Le reste est de l'hygiène d'API — un display_name sur les groupes de rate limits avec dépréciation de group_type, une erreur d'API levée sur les trames d'exception eventstream côté Bedrock, et l'acceptation des types union X | Y au parsing sans lever de TypeError sur des données inconnues.

🛠 Pourquoi c'est utile à savoir pour Lynxter

Le correctif de retry asynchrone est la raison de mettre à jour, pas les nouveautés. Les runs de cette routine tournent derrière un proxy d'egress qui coupe des connexions, et un client qui ne rejoue pas une erreur de connexion en asynchrone perd le run entier. Si un outil Lynxter utilise le SDK Python directement — script de scan de tickets, prototype d'agent support — passe en 1.7.0 et vérifie sur un run réel que les coupures réseau sont bien absorbées plutôt que fatales. C'est un gain de fiabilité mesurable : compte le nombre de runs interrompus avant et après sur deux semaines.

compact_before_next_turn() est ce qui rend la compaction testable sans écrire de plomberie. L'item précédent décrit la primitive serveur ; ici elle devient une ligne dans une boucle d'outils. Si tu veux chiffrer l'intérêt de la compaction sur une conversation de support longue, c'est par là qu'il faut passer plutôt que par des appels manuels à l'API. Réserve honnête : le paramètre est en beta et la 1.7.0 a trois jours — ne l'intègre pas dans un chemin de production avant d'avoir un run de test propre, et garde group_type à l'œil si un monitoring de rate limits existe, puisqu'il est désormais déprécié.
