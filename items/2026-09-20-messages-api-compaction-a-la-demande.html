Contexte étendu

Compacter une conversation longue est le problème central de tout agent qui tourne plus de quelques minutes : la fenêtre de contexte se remplit de résultats d'outils, et la qualité décroche avant même la limite dure. Jusqu'ici, la réponse était à la charge de l'appelant — résumer soi-même, ou laisser un harnais comme Claude Code le faire. Le 14 septembre 2026, Anthropic déplace la primitive dans l'API Messages, en beta derrière l'en-tête compact-2026-09-04. On envoie le paramètre compaction au niveau racine de la requête ; l'API répond avec un bloc compaction signé qui résume les messages envoyés. Sur les requêtes suivantes, ce bloc est placé en tête, à la place des messages qu'il résume.

La signature est ce qui distingue le mécanisme d'un résumé maison. Un bloc produit par le serveur et signé par lui peut être réinjecté sans que le modèle ait à le traiter comme du texte utilisateur potentiellement manipulé, ce qui permet aussi de préserver la validité du raisonnement : sur les modèles à thinking préservé, le thinking des tours gardés mot pour mot après le résumé reste valide. Trois choix restent à l'appelant : quand compacter (ce n'est pas déclenché automatiquement par un seuil), la possibilité de faire tourner la requête de compaction en arrière-plan plutôt que de bloquer le tour en cours, et le nombre de tours récents conservés à l'identique derrière le résumé.

Le calendrier situe l'annonce dans une séquence concurrentielle serrée. Quatre jours plus tôt, le 10 septembre, OpenAI ouvrait son Agents API en beta publique, dont l'argument central est précisément de gérer la compaction du contexte sur les tâches longues — mais comme service managé qui tient la session entière. Anthropic prend l'angle inverse : pas de session managée, une primitive exposée dans l'API Messages que l'appelant orchestre lui-même. Le SDK Python suit dès le 15 septembre avec le paramètre en 1.6.0, puis compact_before_next_turn() dans le tool runner en 1.7.0 le 18.

🛠 Pourquoi c'est utile à savoir pour Lynxter

L'intérêt direct est pour les sessions d'agent longues, pas pour les Routines courtes. Une Routine Cowork qui tourne dix minutes ne sature pas sa fenêtre ; un agent de support qui suit un diagnostic S300X sur plusieurs allers-retours avec logs machine et extraits de doc, si. Sur ce type de session, la compaction à la demande permet de couper le contexte à un moment choisi — typiquement après qu'un diagnostic est établi et avant d'attaquer la remédiation — en gardant les derniers échanges intacts. Action utile : repère dans tes cas de support le point de bascule naturel d'une conversation, et teste un appel compaction à cet endroit précis plutôt que d'attendre une saturation.

La réserve est le statut beta et la portée. L'annonce ne mentionne que l'API Claude, pas Bedrock ni Vertex, et l'en-tête compact-2026-09-04 signale une interface qui peut encore bouger — ne construis rien de contractuel dessus avant une sortie de beta. La bonne façon de l'aborder cette semaine est un essai chiffré sur un cas réel : prends une conversation de support archivée assez longue pour avoir posé problème, rejoue-la avec et sans compaction, et compare deux chiffres — le total de tokens facturés et la qualité du diagnostic final. Si l'écart de tokens est significatif sans perte de qualité, tu as un argument pour l'intégrer au prochain prototype d'agent support.
