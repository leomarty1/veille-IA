Contexte étendu

Le changement est petit dans l'interface et structurant dans le modèle de sécurité. Jusqu'au 14 août, une session Claude Code demandait une approbation à chaque appel d'outil non couvert par une règle explicite ; l'humain devant l'écran était la politique de sécurité. Depuis le 14, sur les plans Pro, Max et Team, un classificateur évalue chaque appel et ne remonte que ce qu'il juge risqué. Anthropic assume le raisonnement : le prompt manuel répété ne produit pas de la vigilance, il produit de la permission fatigue — on approuve sans lire. L'étude publiée à l'appui est directe : sur 1 053 scénarios contenant une commande dangereuse plantée, les relecteurs humains l'ont repérée 143 fois (13.6 %), le classificateur 937 fois (89 %). Le chiffre le plus parlant est celui de la comparaison tête-à-tête : 800 commandes bloquées par auto mode et approuvées par un humain, contre 6 dans le sens inverse.

Il faut lire ces chiffres pour ce qu'ils sont. C'est une étude conduite par le fournisseur, dans un environnement de test construit pour l'exercice, avec des commandes dangereuses délibérément insérées — un protocole qui mesure la détection sur des cas connus, pas la robustesse face à un adversaire qui adapte sa formulation. Aucune réplication externe n'existe à ce jour. Anthropic ne prétend d'ailleurs pas le contraire : la communication accompagne le déploiement d'un rappel explicite que « les classificateurs n'éliminent pas le risque » et que la relecture humaine reste recommandée pour ce qui part en production. La question honnête n'est donc pas « est-ce plus sûr que moi », mais « qu'est-ce qui protège encore quand le classificateur se trompe ». Réponse : les règles de permission déclaratives — deny, denyRead, les restrictions de sandbox — parce qu'elles sont les seules à ne pas dépendre d'un jugement de modèle.

Le contexte de version renforce ce point plutôt qu'il ne le contredit. Sur les sept jours entourant la bascule, trois correctifs touchent directement auto mode. La 2.1.225 (8 août) corrigeait un comportement où le refus, par un filtre de sécurité, de la propre vérification de permission du modèle était compté dans la limite de blocages consécutifs — l'action restait refusée, mais le modèle est désormais invité à passer à autre chose plutôt qu'à réessayer. La 2.1.227 (10 août) réparait un auto mode qui échouait sur chaque appel d'outil chez les utilisateurs désactivant l'en-tête d'attribution via CLAUDE_CODE_ATTRIBUTION_HEADER sur les connexions API directes. Et la 2.1.233 (14 août), le jour même de la bascule, corrige sous Windows des arrêts répétés pour approbation manuelle sur des commandes Bash aussi ordinaires que cd <dir> && <commande> > fichier — une régression introduite la veille par la 2.1.232, dont une partie des changements de permission Bash (symlinks Cygwin, redirections < fichier) a d'ailleurs été purement et simplement annulée en attendant une version plus étroite.

🎯 Pourquoi c'est important pour Lynxter

L'action prioritaire est un audit des règles deny, repo par repo, et elle est urgente parce que le défaut a déjà basculé. Tant que le prompt manuel existait, un oubli dans .claude/settings.json se rattrapait à l'écran. Ce n'est plus le cas : ce qui n'est pas explicitement refusé est arbitré par un classificateur. Pour Lynxter, la liste de ce qui doit être listé en deny est courte et connue — profils firmware S300X/S600D en production, clés et scripts de signature, procédures de flash, exports de données client, tout chemin contenant des credentials. Un point d'attention hérité de la semaine précédente : les entrées denyRead écrites avec un slash final (denyRead: "~/.aws/") étaient silencieusement contournables sous Linux et macOS jusqu'à la 2.1.224 du 7 août. Si tes règles datent d'avant, elles méritent une relecture doublée d'une vérification de version.

Le second réflexe est de calibrer plutôt que de subir. Auto mode reste configurable : les sessions qui touchent au firmware, aux profils machine ou au code livré client gagnent à rester en approbation explicite, celles qui font du tri de tickets, de la rédaction de documentation ou de l'analyse de logs n'ont aucune raison de coûter une interruption toutes les trente secondes. La bonne granularité n'est pas le compte, c'est le repo. Sur les 800 blocages qu'un humain aurait approuvés, la leçon transposable à Lynxter est simple : le classificateur est probablement meilleur que toi sur la commande destructive noyée dans une session de trois heures, et probablement moins bon que toi sur ce qui est spécifiquement critique pour ton métier — parce qu'il ne sait pas qu'un fichier de profil d'extrusion vaut plus qu'un fichier de test.

Enfin, il faut traiter cette surface comme du logiciel jeune. Trois correctifs sur auto mode en sept jours, une régression Windows corrigée le jour même de la bascule du défaut, et un revert partiel des changements de permission Bash de la veille : ce n'est pas un signal d'alarme, c'est un signal de maturité en cours. Pratique : épingler la version de Claude Code utilisée sur les postes qui touchent au firmware, lire le changelog avant de monter de version, et garder une session de contrôle en mode manuel pour les opérations irréversibles. Le coût de cette discipline est de quelques minutes par semaine ; le coût d'un profil de production écrasé par un agent est d'une journée de production.
