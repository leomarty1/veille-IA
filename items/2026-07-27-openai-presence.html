Contexte étendu

OpenAI lance Presence le 22 juillet 2026, un produit entreprise pour déployer des agents voix et chat sur des workflows client-facing et internes : support client, ventes sortantes, tickets IT. Chaque déploiement est scopé par tâche, avec des policies explicites qui définissent ce que l'agent peut faire, à quel moment il doit demander une approbation, et quand un humain reprend la main. C'est un produit de gouvernance autant que d'IA : le périmètre d'action est le premier objet de configuration.

La particularité structurante : aucune voie self-serve ni API publique. Chaque installation passe par les Forward Deployed Engineers d'OpenAI ou des intégrateurs agréés, qui câblent l'agent aux systèmes métier du client. C'est un choix de go-to-market inverse d'un produit API classique — OpenAI garde la main sur chaque déploiement, ce qui verrouille le client sur l'intégrateur mais garantit un niveau de fiabilité contractualisé.

Les métriques publiées viennent de la propre ligne support anglophone d'OpenAI : ~75 % des demandes entrantes résolues sans humain et -15 % de handoffs sur 10 jours. La boucle d'amélioration est confiée à Codex : il analyse les interactions de production et les escalades, propose des mises à jour de comportement, qui sont validées par un humain avant mise en ligne — un pattern d'amélioration continue human-in-the-loop appliqué au comportement de l'agent lui-même, pas seulement à son prompt.

🛠 Pourquoi c'est utile à savoir pour Lynxter

Le modèle de gouvernance est directement transposable à un agent support S300X/S600D. Le triptyque de Presence — périmètre d'action par tâche + points d'approbation humaine explicites + amélioration continue supervisée — est exactement le cadre qu'il faut poser avant de mettre un agent support en production chez Lynxter. Reproduis-le sur ta stack Claude Code/MCP : définis pour chaque type de ticket ce que l'agent peut faire seul (rechercher dans la base de connaissance, proposer un diagnostic), ce qui exige une validation (envoi d'une réponse client, ouverture d'un RMA), et ce qui remonte à un humain. Les caps de session et le strictAllowlist de Claude Code v2.1.219 fournissent déjà les garde-fous techniques pour ça.

Le verrou FDE est l'argument pour rester sur une stack auto-hébergée. Presence n'a pas d'API self-serve : chaque changement passe par les Forward Deployed Engineers ou un intégrateur agréé — dépendance forte, cycle d'itération lent, et opacité sur le comportement réel de l'agent. Face à ça, la stack Claude Code + MCP que Lynxter peut piloter en interne garde l'auditabilité et la vitesse d'itération. Retiens le pattern de gouvernance de Presence, pas son modèle de livraison : construis l'équivalent en interne, avec Codex-style d'analyse des escalades remplacé par un run Claude Code hebdomadaire qui relit les tickets escaladés et propose des ajustements de prompt/policy validés par le support.
